## Canary

Если эти правила не соблюдены — значит файл не прочитан.

1. 🏍️ Начинай первое сообщение в сессии с маркера `🏍️ MotoPhD`.
2. Коммит-сообщения — Conventional Commit.
3. Тронул файлы → сам не коммить без просьбы. Имя коммита предлагай **только** тому, кто сам работает
   с git (коммитит руками, говорит git-терминами) — это Дима. Для нетехнического пользователя (Аня)
   git невидим: ни имени коммита, ни команд, ни «вставь в терминал». Просит «оформи/сохрани» — весь
   git делаешь ты сам и молча (раздел «Как работать…», правило 7).

*(#1 — заменяемая тревожка «агент прочитал файл»; #2–3 — рабочие правила. Полный git-процесс — [docs/GITFLOW.md](./docs/GITFLOW.md))*

## Как работать над продуктовыми задачами

Правила для любой сессии; написаны в первую очередь под работу Ани (нетехнический пользователь).

1. **Сначала вопросы, потом код.** На продуктовый запрос («сделай», «поменяй», «добавь») — задай
   простые НЕтехнические вопросы, пока картина не ясна: что именно, на какой странице, как должно
   выглядеть, зачем, как это должно вести себя на телефоне. Не выдумывай детали сам. Не сыпь жаргоном.
2. **Дробление обязательно.** Запрос шире одного компонента → предложи нумерованный список маленьких
   подзадач и делай ТОЛЬКО первую. После каждой — покажи результат и спроси, двигаться ли дальше.
   «Переделай страницу целиком» одним заходом — отказ: только по кусочкам.
3. **Тесты обязательны.** Изменил поведение — напиши/обнови тест (образцы:
   `src/lib/access/hasPaidAccess.test.ts`, `src/components/prototype/FaqAccordion/FaqAccordion.test.tsx`,
   `e2e/smoke.spec.ts`). Завершать работу можно только при зелёных `pnpm lint`, `pnpm typecheck`, `pnpm test`.
4. **Код-стиль.** [docs/CODE_STYLE.md](./docs/CODE_STYLE.md) обязателен (размеры файлов, колокация,
   BEM). Новые npm-зависимости — только после явного «да» пользователя.
5. **Запретные зоны** (меняет только Дима): `deploy/`, `.github/`, `src/migrations/`,
   `src/payload.config.ts`, `src/collections/`, `Dockerfile`. Задача туда лезет — останови работу.
   Пользователю объясни **человеческими словами**, без путей и терминов: «это внутренняя
   техническая часть, её настраивает Дима» — а не «это запретная зона `deploy/`».
   *Ввод данных ≠ структура:* заполнять готовые поля в админке (тексты курсов/уроков) — можно;
   менять, *какие поля вообще есть* — это `src/collections/`, к Диме. «Перенести тексты в админку»
   звучит как контент, но требует новых полей → тоже к Диме.

6. **Не разводи архитектурный аудит, когда не просят.** Не открывай сессию списком «что меня
   насторожило» и не предлагай пользователю чинить доступ / безопасность / схему БД / тесты — это
   не её решения, она их не оценит. Заметил такой момент — максимум одна фраза «это тех-вопрос для
   Димы, отметь ему», без разбора и без «давай починим». Глубокую проверку Дима запускает сам
   (`/code-review` или прямой запрос) — тогда аудит уместен.
7. **Два слова Ани — git и деплой. Всё делаешь ты сам и молча.** Только по её явной команде:
   - **«оформляй» / «сохраняй»** — вся git-движуха: ветка `feature/<slug>` → Conventional Commits →
     push → PR (что/зачем/как проверить) → `gh pr merge --auto --squash` (вольётся в `main` на зелёных
     проверках). Прямой пуш в `main` запрещён всегда.
   - **«выкладывай» / «публикуй»** — деплой `main` в прод: `gh workflow run deploy.yml`. Сперва
     убедись, что её последняя правка **реально в `main`** (PR влился, проверки зелёные). Ещё идут —
     не деплой, скажи «проверки идут, выложу как вольётся» и дождись.
   - **«оформляй и выкладывай»** в одном сообщении — по очереди: оформил → дождался, что влилось →
     выложил.

   Ничего из этого не показывай командами/жаргоном и не проси вставлять в терминал. Отвечай
   по-человечески: «сохранила, проверки идут» / «выложила, через пару минут будет на motophd.com».
   Без явной команды git и деплой не трогать (canary-правило 3).
8. **По-русски и без жаргона.** Не открывай сессию списком правил и перечислением того, чего ты
   «не будешь делать» — просто поздоровайся, в двух словах скажи, что за проект, и спроси, что
   хочется поделать. Слова *сервер, база, деплой, git, PR* сами по себе ей ничего не говорят: не
   сыпь ими. Если слово правда нужно — объясни его одной простой фразой прямо на месте и говори её
   языком («оформить», «выложить на сайт», «зелёные галочки»). Непонятные слова с пояснениями — в
   [docs/ANYA.md](./docs/ANYA.md).

## Команды

```bash
pnpm install
pnpm db:up          # локальный Postgres (brew services). Первый раз: pnpm db:setup
pnpm payload migrate
pnpm seed
pnpm dev
pnpm payload
pnpm generate:types
pnpm seed
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm build
```

`pnpm test` — юнит/компонент (Vitest). `pnpm test:e2e` — смоук по страницам (Playwright,
порт 3100): нужны дев-Postgres (`pnpm db:up`), `pnpm seed` и свежий `pnpm build`.

**База локально, без Docker** (порт 5432, БД/роль `motophd`):

| Команда | Что делает |
|---|---|
| `pnpm db:up` / `pnpm db:down` | старт/стоп локального Postgres через brew services |
| `pnpm db:setup` | создать роль и базу (идемпотентно; владелец базы обязан быть `motophd`) |
| `pnpm db:reset` | снести базу и собрать заново: setup → migrate → seed |
| `pnpm db:psql` | psql-консоль к дев-базе |
| `pnpm db:up:docker` | старый путь через Docker (порт 5433) — если понадобится |

После правок `payload.config.ts` (особенно плагинов) — `pnpm payload generate:importmap`,
иначе админка отдаёт белый экран.

Текущая версия — сайт читает контент из Payload, прод развёрнут (OVH + GHCR + Caddy + Cloudflare,
деплой кнопкой в Actions), тестовый фундамент стоит. Дальше по бэклогу: медиа (R2/Stream),
платежи, мониторинг, бэкапы — [docs/tbd/](./docs/tbd/README.md).
