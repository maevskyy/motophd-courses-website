# Task 6 — Платёжный каркас: PaymentProvider, mock-флоу, вебхук

**Depends on:** 2 (модель контента), 14/15/16 (вход и гейт доступа — уже в коде)
**Goal:** полный флоу покупки работает на mock-провайдере: выбор тарифа → серверный расчёт цены →
`Purchase{pending}` → «оплата» → колбэк с проверкой подписи → `Purchase{paid}` → аккаунт и доступ.
WayForPay подключается сменой провайдера, без переписывания флоу.

## Продуктовые решения

1. **Аккаунт создаётся в момент старта чекаута, доступ — после оплаты.** `Purchases.user`
   обязателен, поэтому гостю негде «повисеть» до колбэка. Гость вводит email → сразу создаём
   `Users{role:'student'}` со случайным паролем (никуда не показываем и не храним в открытом виде)
   → создаём `Purchase{pending}` на него. Не оплатил — остался аккаунт с `pending`-покупкой:
   доступа он не даёт, войти в него нельзя (пароль никому не известен). Email уже занят —
   **линкуем покупку к существующему аккаунту** (см. решение 3 про авто-вход).
2. **Провайдер включается явно, дефолта нет.** `PAYMENTS_PROVIDER` = `mock` | `wayforpay`.
   Переменная не задана ⇒ чекаут выключен: кнопка показывает fallback-блок «не получается
   оплатить — свяжитесь с нами» (требование BUSINESS_RULES), заказ не создаётся. Так прод,
   где боевых ключей ещё нет (блокер — ФОП Влада), безопасен по умолчанию, а mock физически
   не может выдать доступ в проде. Цена решения: в `.github/workflows/ci.yml` в job `e2e`
   нужно добавить `PAYMENTS_PROVIDER: mock` в `env` контейнера — **правку делает Дима**
   (запретная зона по AGENTS.md), она однострочная и обязана попасть в тот же PR.
3. **Авто-вход после оплаты — только для аккаунта, созданного этим же заказом.** Одноразовый
   `postPaymentToken` генерируется **на чекауте** (тогда же он уезжает в `returnUrl`
   провайдера: `/checkout/success?order=<ref>&t=<token>`), TTL 60 минут. Страница успеха
   пускает внутрь только если заказ уже `paid`, токен совпал, не просрочен и не погашен;
   вход выдаётся штатным Payload-путём — `payload.forgotPassword({ disableEmail: true })` →
   `payload.resetPassword()` возвращает токен сессии → кука `payload-token` (как в
   `src/lib/auth/actions.ts`). Токен гасится, человек попадает в кабинет.
   **Если покупка привязана к существующему аккаунту — `postPaymentToken` не выдаётся вообще**,
   страница успеха просто просит войти. Иначе покупка курса за €29 на чужой email становится
   захватом чужого аккаунта.
   *Известное ограничение (записать честно):* пока нет Resend, покупатель, закрывший вкладку
   или оплативший с другого устройства, доступ сам не получит — только ручная выдача пароля
   через админку. Письмо в этой задаче = запись в лог.
4. **Повторная покупка того же курса отклоняется на чекауте.** Есть `paid` покупка курса и
   запрошен `standard`/`feedback` → ошибка «курс уже куплен» + ссылка в кабинет, заказ не
   создаётся. `feedback_upgrade` разрешён только при существующей `paid`-покупке `standard`
   на этот курс и только один раз.
5. **Промокоды — отдельная коллекция** ровно с полями из ТЗ §5: `code`, `discountType`
   (`percent`|`fixed`), `value`, `maxUses`, `usedCount`, `validFrom`, `validTo`, `active`.
   Код нормализуется в верхний регистр и уникален. Скидка применяется к итоговой сумме тарифа
   (в том числе к `feedback_upgrade`). `usedCount` инкрементится **на оплате, не на чекауте**.
   Гонка при одновременных колбэках в MVP не решается — лимит может быть превышен на 1–2;
   это принято осознанно (Redis/транзакций нет, ADR-4).
6. **Сумма к оплате — минимум €1.** Скидка не может обнулить заказ: 100% промокоды в MVP
   запрещены (иначе нужен отдельный флоу «оплата без провайдера»). Округление — до 2 знаков,
   half-up: 29 × −10% = 26.10.
7. **Страницы результата — минимальные заглушки, но настоящие:** `/[locale]/checkout/success`
   (по `orderReference`; с валидным `postPaymentToken` — авто-вход и редирект в кабинет) и
   `/[locale]/checkout/fail` (ссылка вернуться на курс + fallback-контакт). Без них флоу не
   проверяется e2e. Красивый UI чекаута с двумя чекбоксами — отдельная задача.
8. **Промокод и email в UI — минимальные поля** в `PricingBox` (один input под email для гостя,
   один под промокод). Это не «UI чекаута», а минимум, без которого флоу не запускается.

## Scope

**Схема и миграция** (запретная зона — делает Дима):

- `src/collections/Purchases.ts`: `orderReference` (text, `unique: true`, `index: true`, не
  required — у `manual`/seed-покупок его нет), `promoCode` (relationship → `promoCodes`,
  необязательный), `paidAt` (date), `providerPayload` (json, сырой колбэк для разбора споров),
  `postPaymentToken` (text, index) + `postPaymentTokenExpiresAt` + `postPaymentTokenUsedAt`
  (date). Коллекция читается только админом — дополнительный field-level access не нужен.
- Новая коллекция `src/collections/PromoCodes.ts` (поля — решение 5), CRUD только админу,
  регистрация в `src/payload.config.ts`.
- `pnpm payload migrate:create` → новый файл в `src/migrations/` + `pnpm generate:types`.
- **Порядок с задачей 5 (медиа):** обе задачи меняют схему. Миграции создаются
  последовательно: кто первым уходит в реализацию — тот первым создаёт миграцию, второй
  ребейзится и пересоздаёт свою поверх. Пересечений нет: `Purchases`/`PromoCodes` — эта задача,
  `Media`/`Lessons` — задача 5.

**`src/lib/payments/`:**

- `types.ts` — интерфейс `PaymentProvider`: `name`, `createCheckout(order)` → куда отправить
  человека, `verifyCallback(request)` → `{ ok, orderReference, status, providerTxnId, raw }`,
  `buildAck(result)` → тело ответа провайдеру. Плюс доменные типы заказа.
- `pricing.ts` — чистые функции без I/O: цена тарифа из `Course`, `feedback_upgrade` =
  `priceFeedback − priceStandard`, применение промокода, округление, минимум €1.
- `promoCodes.ts` — поиск по нормализованному коду и валидация (активен, окно дат, лимит).
- `orderReference.ts` — генерация ссылки заказа (устойчивый префикс + случайная часть,
  символы и длина — по ограничениям WayForPay, см. ниже).
- `checkout.ts` — server action: тариф, email гостя, промокод → проверки решения 4 →
  создание/линковка `Users` → `Purchase{pending}` (+ `postPaymentToken`, только если аккаунт
  создали здесь же) → `createCheckout` провайдера → редирект.
  Цена приходит **только** отсюда, из клиента не принимается ничего, кроме тарифа/промокода/email.
- `fulfilment.ts` — то, что происходит на успешном колбэке: идемпотентный переход
  `pending → paid` (повтор по тому же `orderReference` — no-op), `paidAt`, `providerTxnId`,
  `providerPayload`, инкремент `usedCount` промокода, лог-заглушка письма.
- `session.ts` — погашение `postPaymentToken` на странице успеха и выдача куки (решение 3).
- `notifications.ts` — заглушка письма через `payload.logger.info` (Resend — отдельная задача).
- `registry.ts` — выбор провайдера по `PAYMENTS_PROVIDER`, `null` если не задан.
- `providers/mock/` — мгновенный success/fail; «страница банка» — наша же
  `/[locale]/checkout/mock` (доступна только при `PAYMENTS_PROVIDER=mock`), кнопки «Оплатить» и
  «Отклонить» бьют в **тот же** боевой роут колбэка с валидной mock-подписью
  (HMAC-SHA256 на `PAYLOAD_SECRET`). Так e2e проверяет реальный путь, а не обход.
- `providers/wayforpay/` — скелет: сборка запроса, подпись, разбор и проверка колбэка,
  подписанный ответ-подтверждение. Детали — в разделе «WayForPay» ниже.

**Роуты и страницы:**

- `src/app/api/payments/[provider]/callback/route.ts` — POST: провайдер из сегмента, сырое тело
  (не `request.json()`, см. WayForPay), `verifyCallback` → при невалидной подписи 400 и никаких
  изменений → `fulfilment` → ответ в формате провайдера (для WayForPay — подписанный JSON-ack).
- `src/app/api/payments/[provider]/return/route.ts` — POST-приёмник `returnUrl` (провайдер
  возвращает человека POST-ом), делает 303 на `/[locale]/checkout/success|fail`.
- `src/app/(marketing)/[locale]/checkout/success/page.tsx`, `.../fail/page.tsx`,
  `.../mock/page.tsx`.
- `src/components/prototype/PricingBox/PricingBox.tsx` — кнопка отправляет форму в server action
  (тариф выбранной опции, email гостя, промокод); дисклеймер-чекбокс остаётся обязательным;
  при выключённом провайдере — fallback-блок.

**Тексты, seed, env:**

### WayForPay

Проверено по [wiki.wayforpay.com](https://wiki.wayforpay.com/en/view/852102) и официальному
[php-sdk](https://github.com/wayforpay/php-sdk). Отдельного sandbox-домена нет — тот же
`https://secure.wayforpay.com/pay`, «тестовость» задаётся мерчант-аккаунтом. Публичный тестовый
мерчант: `test_merch_n1` / ключ `flk3409refn54t54t*FNJRET`
([wiki 852472](https://wiki.wayforpay.com/en/view/852472)).

- **Создание платежа.** Вместо авто-сабмита HTML-формы использовать серверный вариант:
  POST на `https://secure.wayforpay.com/pay?behavior=offline` → ответ `{"url": "..."}` →
  наш `createCheckout` возвращает этот URL, страница курса делает обычный редирект.
  Обязательные поля: `merchantAccount`, `merchantDomainName`, `merchantSignature`,
  `merchantTransactionSecureType: 'AUTO'`, `orderReference` (EN-версия доки помечает его
  необязательным, UK — обязательным; он входит в подпись и в сверку ⇒ передаём всегда),
  `orderDate` (unix, секунды),
  `amount` (точка-разделитель), `currency`, `productName[]`, `productPrice[]`, `productCount[]`.
  `serviceUrl` формально необязателен — без него не будет вебхука, передаём всегда;
  плюс `returnUrl`, `clientEmail`, `language`, `merchantTransactionType: 'SALE'`
  (не `AUTH`, иначе деньги только блокируются и доступ выдавать нельзя).
- **Подпись запроса:** `HMAC-MD5(строка, merchantSecretKey)`, hex lowercase, UTF-8,
  разделитель `;`. Порядок: `merchantAccount; merchantDomainName; orderReference; orderDate;
  amount; currency;` затем **все** `productName`, затем **все** `productCount`, затем **все**
  `productPrice` (плоско, не парами). `amount` попадает в подпись **ровно той строкой**, что
  уходит в поле: `100` и `100.00` дают разные подписи ⇒ формат фиксируется в одном месте.
- **⚠️ Печатные примеры подписи в доке недостоверны — в тесты их не брать.** Проверено
  побайтово: на [странице Purchase](https://wiki.wayforpay.com/view/852102) для одного и того же
  примера приведены **две разные** подписи (`3f787303ac524389b4a76383f9508251` в тексте UK/RU
  и `b95932786cbe243a76b014846b63fe92` в таблице, HTML-форме и EN-версии), а её же PHP-снипет
  (`hash_hmac("md5", $string, $key)`) на её же входных данных даёт **третье** значение
  `4941ea0c7f5b4833c2bd06b1fefcdc0b`. Ни одно из двух печатных значений не воспроизводится
  (проверено 168 комбинаций: HMAC/конкатенация, UTF-8/CP1251, md5/sha1/sha256, оба ключа).
  Вдобавок подписываемая строка начинается с `test_merchant`, а форма ниже отправляет
  `merchantAccount=test_merch_n1` — пример противоречит сам себе. В примерах колбэка и
  «правильного ответа мерчанта» поле подписи вообще пустое (`"merchantSignature":""`,
  `"signature":""`), так что валидной подписи в доке нет ни одной — фикстуры для тестов
  брать оттуда нельзя.
- **Алгоритм при этом верный.** Собственный генератор WayForPay
  (`GET https://wiki.wayforpay.com/wiki/default/generate-hmac?string=…&key=…`, живой эндпойнт
  их же [страницы-генератора](https://wiki.wayforpay.com/ru/wiki/default/test)) на документированной
  строке возвращает то же `4941ea0c…`, что и обычный HMAC-MD5. То есть врут **примеры**, а не
  спецификация. Векторы ниже посчитаны нами и **сверены с этим генератором один-в-один** —
  их и брать в юнит-тест (ключ публичного тестового мерчанта `flk3409refn54t54t*FNJRET`):

  ```
  purchase: test_merch_n1;example.com;ORD-1002;1700000000;100.00;UAH;Test Product;1;100.00
            → d9e252e426b622682260c01afcb5808f
  purchase: test_merch_n1;www.market.ua;ORD-1001;1415379863;1547.36;UAH;Course A;Course B;1;1;1000;547.36
            → 474606dbda8589b9243ed590bd442510
  callback: test_merch_n1;ORD-1002;100.00;UAH;541963;41****8217;Approved;1100
            → 688dbd85ec0db0c6de8bd546fb5aa644
  ack:      ORD-1002;accept;1700000100 → 1e425f731eda97710b61419cb8fcc72a
  ```

  Векторы фиксируют нашу сборку строки и HMAC; факт приёмки на стороне эквайринга
  подтверждается ручным прогоном на тестовом мерчанте (PR 2).
- **Колбэк (`serviceUrl`).** POST, тело — **сырой JSON без `Content-Type: application/json`**
  ⇒ `request.json()` использовать нельзя: читаем `await request.text()` и парсим сами,
  с фолбэком на form-urlencoded. Подпись колбэка — те же HMAC-MD5 и `;` по 8 полям:
  `merchantAccount; orderReference; amount; currency; authCode; cardPan; transactionStatus;
  reasonCode`. Успех — **только `transactionStatus === 'Approved'`** (сравнивать регистро-
  независимо: в доке встречается `inProcessing`); `WaitingAuthComplete` доступ не открывает.
  `reasonCode: '1100'` = ок, `1112` = дубль `orderReference`, `1113` = плохая подпись.
- **Ответ на колбэк:** JSON `{orderReference, status: 'accept', time, signature}`, подпись —
  HMAC-MD5 по `orderReference;status;time` (тот же `time`, что в теле). Без корректного ответа
  WayForPay повторяет запрос **до 4 суток** — поэтому на валидно подписанный колбэк любого
  статуса отвечаем подписанным `accept` (200), и только на **невалидную подпись** — 400.
- **`returnUrl` — это POST от браузера (form-urlencoded), а не GET.** Страница Next на POST
  ответит 405, поэтому `returnUrl` указывает на роут-обработчик, который делает 303-редирект
  на `/[locale]/checkout/success`. Данными `returnUrl` **не доверяем** — доступ выдаётся
  только по `serviceUrl`-колбэку.
- **`orderReference`.** Повтор = отказ `1112`, переиспользовать нельзя. Ограничения алфавита
  и длины дока не публикует ⇒ ограничиваемся `[A-Za-z0-9._-]`; `;` запрещён (он же разделитель
  подписи — риск коллизии).
- **Валюта.** `currency: 'EUR'` технически поддерживается, но по
  [справке WayForPay](https://help.wayforpay.com/view/1737828) списание с иностранных карт идёт
  **в гривне с конвертацией**, а зачисление мерчанту — только в гривне. Отдельного EUR-счёта
  дока не описывает ⇒ вопрос к WayForPay до боевого подключения (см. Открытые вопросы).
- **Apple Pay / Google Pay** на платёжной странице WayForPay включаются автоматически, без
  отдельной интеграции и заявки — нашей работы не требуют.
- Тестовых номеров карт в официальной доке **нет** (проверены EN и UK версии) — запрос в
  support@wayforpay.com.

## Acceptance criteria

- **E2e mock-флоу (гость):** на странице курса гость вводит email → «оплата» на mock-странице →
  возвращается уже залогиненным, курс открывается в `/learn/<slug>`, в БД одна
  `Purchase{status:'paid', provider:'mock'}`.
- **E2e mock-флоу (промокод):** с `MOTO10` сумма заказа 26.10, а не 29.
- **E2e отказ:** «Отклонить» на mock-странице ведёт на `/checkout/fail`, покупка остаётся
  `pending`, доступа нет.
- **Идемпотентность:** повторный колбэк с тем же `orderReference` — 200 и no-op: вторая
  покупка не создаётся, `usedCount` промокода не растёт второй раз.
- **Невалидная подпись — 400**, `Purchase` не меняется (проверить и для mock, и для WayForPay).
- **Захват аккаунта невозможен:** покупка на email существующего пользователя не выдаёт
  `postPaymentToken` и не логинит покупателя (тест обязателен).
- **Unit `pricing`:** три тарифа × (percent | fixed | без промокода), `feedback_upgrade` = 100,
  округление 26.10, минимум €1, отказ при 100%-скидке.
- **Unit `promoCodes`:** просрочен, не начался, исчерпан `maxUses`, `active:false`, неизвестный код.
- **Unit подписи WayForPay:** четыре регрессионных вектора из раздела «WayForPay» (два запроса,
  колбэк, ack) сходятся; испорченная подпись колбэка отвергается; `transactionStatus` не `Approved`
  (например `WaitingAuthComplete`) доступ не открывает, но получает подписанный `accept`;
  колбэк парсится из сырого тела без `Content-Type: application/json`.
- **Unit `checkout`:** повторная покупка отклонена, `feedback_upgrade` без базовой покупки
  отклонён, цена из клиента игнорируется.
- **Компонентный тест `PricingBox`:** без принятого дисклеймера заказ не отправляется;
  при выключённом провайдере вместо кнопки — fallback-блок. (Своих тестов у компонента сейчас нет,
  но кнопка перестаёт быть тостом-заглушкой и начинает создавать заказ.)
- Зелёные `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:e2e`.

## Решение о провайдере принимается перед PR 2, не перед PR 1

Проверка WayForPay при груминге вскрыла две вещи, которые к коду отношения не имеют, но
определяют, писать ли вообще скелет WayForPay:

- **Регуляторный риск.** В мае 2023 НБУ не переоформил лицензию — приём платежей встал у всех
  клиентов сервиса примерно на неделю (платежи временно проводили через LiqPay и Raiffeisen,
  лицензию вернули 08.06.2023). 09.02.2026 НБУ оштрафовал компанию на 1,7 млн грн за нарушение
  закона «Про платіжні послуги». Оба события — не технические, обойти их кодом нельзя.
- **EUR и НДС ЕС.** WayForPay зачисляет мерчанту **только в гривне**, а с иностранных карт
  списывает **в гривне с конвертацией** — прайс в евро остаётся витриной. Отдельно: при продаже
  цифровых услуг физлицам в ЕС продавец, не учреждённый в ЕС, обязан начислять НДС страны
  покупателя **с первой продажи** (ст. 58 Директивы 2006/112/EC; порог €10 000 по ст. 59c(1)(a)
  работает, только если продавец учреждён в одном из государств-членов — ФОП под него не подпадает),
  то есть
  17–27% сверху плюс квартальная отчётность в non-Union OSS. Это дороже любой эквайринговой
  комиссии. Merchant-of-record платформа (Paddle, FastSpring) снимает обязанность юридически —
  ст. 9a Имплементационного регламента (ЕС) 282/2011, действительность подтверждена Судом ЕС
  (C-695/20 Fenix/OnlyFans, 28.02.2023). Украина не входит в стоп-лист продавцов Paddle;
  Stripe Украину не поддерживает вовсе.

**Что это меняет в работе.** PR 1 провайдеро-независим: серверный прайсинг, `Purchases`,
промокоды, идемпотентный колбэк, создание аккаунта и выдача доступа нужны при любом исходе —
его можно делать сразу. PR 2 (скелет WayForPay) откладывается до ответа Димы: если решение
уйдёт в MoR, чекаут будет строиться на стороне платформы и скелет окажется выброшенной работой.

## Разрез на PR

Оценка целиком — ~3.5–4 дня, поэтому режем:

- **PR 1 — деньги и mock-флоу** (~2–2.5 дня): схема + миграция + `PromoCodes`, `pricing`,
  `promoCodes`, интерфейс провайдера, mock, checkout-action, роуты колбэка и `returnUrl`,
  fulfilment, success/fail/mock-страницы, `PricingBox`, seed, тексты, юниты + e2e.
- **PR 2 — скелет WayForPay** (~1–1.5 дня): сборка запроса и подписи, разбор и проверка колбэка,
  подписанный ack, конфиг тестового мерчанта, юниты с векторами, ручной прогон на
  `test_merch_n1` (и письмо в саппорт из открытых вопросов).

PR 1 самодостаточен: после него флоу покупки полностью работает на mock.
